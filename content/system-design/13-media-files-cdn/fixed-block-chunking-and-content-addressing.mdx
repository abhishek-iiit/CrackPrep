## The unit of transfer should not be the file

A 4 GB disk image that changes 8 MB in the middle should not cost 4 GB on the wire. Fixed-size block chunking splits a file into blocks of a chosen size — 1 MiB, 4 MiB, sometimes smaller for chattier sync — hashes each block, and treats the hash as the block's identity in a blob store. Content addressing means the key *is* the hash: put is idempotent, two uploads of identical bytes converge on one object, and "do you have this block?" is a cheap existence check.

This is the mechanism under many sync and backup systems; 13.09 Remote File Sync Design covers when to invoke it. The lesson here is how the split and the address interact — and what breaks when the block size or the hash is wrong for the workload.

## Fixed blocks end to end

<Steps>
  <Step title="Choose a block size">
    Larger blocks mean fewer hashes, less metadata, and better throughput on fat networks; they also mean a one-byte edit dirties an entire block. Smaller blocks improve delta granularity and hurt listing and request-rate overhead. 1–4 MiB is a common default for LAN/cloud sync; tune down when edits are tiny and frequent.
  </Step>
  <Step title="Split and hash">
    Read the file sequentially, emit blocks of fixed length (last block short), compute a cryptographic hash per block (SHA-256 is the usual interview-grade choice). The file becomes an ordered list of hashes — a blocklist — plus file-level metadata.
  </Step>
  <Step title="Upload missing blocks only">
    For each hash, ask the block store if it exists; PUT only the misses. Content addressing makes retries safe: a second PUT of the same hash is a no-op or an overwrite of identical bytes.
  </Step>
  <Step title="Publish the new blocklist">
    Once all blocks are present, write the versioned file metadata that points at the ordered hash list (13.11 Blocklist Versioned File Metadata). Readers assemble the file by fetching blocks in order — or sparse-read a range by mapping byte offsets to block indices.
  </Step>
</Steps>

Dedup scope follows how you key the store: global namespaces dedupe across every user (maximum savings, maximum cross-tenant fingerprinting concern); per-tenant or per-user namespaces isolate savings and blast radius. Encryption-before-hash (client-side encryption) kills cross-user dedupe unless you use convergent encryption deliberately — and convergent encryption has known confirmation-of-file attacks you should name if you propose it.

## Fixed versus content-defined chunking

Fixed chunking is simple and maps cleanly to byte ranges: offset `O` lives in block `O / block_size`. Its failure mode is the **insertion shift**: insert one byte at the start of a file and every subsequent fixed block changes, so the delta looks like a full rewrite. Content-defined chunking (rolling hash / Rabin-style CDC, as in rsync-inspired and many backup agents) places boundaries where content fingerprints match a pattern, so an insertion typically only invalidates nearby chunks.

| Approach | Delta quality on inserts | Implementation | Natural fit |
| --- | --- | --- | --- |
| Fixed-size blocks | Poor when edits shift alignment | Trivial split, trivial offset math | Sync with mostly overwrite-in-place, VM disks with sparse writes, teaching designs |
| Content-defined (rolling hash) | Good — boundaries absorb shifts | Rolling hash CPU cost, variable sizes, harder range math | Backup agents, rsync-like protocols, document-ish files with inserts |
| Whole file | Worst | One object key | Small files where chunk overhead exceeds savings |

CDC variable sizes also complicate SLOs: a "block" might be 100 KB or 8 MB unless you clamp min/max. Fixed blocks keep pack files and caches predictable.

<Callout type="gotcha">
Content addressing is only as trustworthy as the hash and the verification path. Always verify hash on write (and ideally on read) against the bytes; a corrupted block stored under the "right" key poisons every file that references it. End-to-end checksums (07.20) are the same discipline at a different layer.
</Callout>

## GC, sharing, and the cost of immortal blocks

Blocks outlive any single file version. GC requires reference counting or mark-and-sweep from live blocklists — run too eagerly and you delete a block a concurrent upload still needs; run too rarely and storage grows without bound as old versions accumulate. Immutability helps: never mutate a hash's bytes in place; only add or GC.

Shared blocks couple failure domains: one bad disk scrub affecting a hot block can hit many files. Replication and scrubbing policies for the block store matter more than for unique whole-file objects.

## In an interview

Lead with the cost you avoid: "I chunk large files into fixed content-addressed blocks so an edit only reuploads dirty blocks and retries are idempotent." Know one number — pick a block size and say what edit pattern would make you shrink it. When asked about rsync, explain insertion shift versus rolling-hash CDC without dismissing fixed blocks: they win on simplicity and range mapping. Name GC and hash verification as the failure modes before the interviewer does.
