## Avatars are a caching problem wearing a face

Almost every product needs a small square image for a user. The naive path — `/api/users/\{id\}/avatar` hitting an app server on every comment render — turns profile photos into a latency and auth burden on the hottest HTML and JSON paths. Gravatar's enduring idea is simpler: **an avatar is a URL derived from an identity hash**, served as a static object from a CDN, with a deterministic default when nothing was uploaded.

You do not have to outsource to Gravatar to steal the shape. Many systems build an internal twin: hash email or user id → object key → CDN.

## The URL contract

Classic Gravatar-style:

```text
https://cdn.example.com/avatar/{hash}?s=80&d=identicon
```

- **`hash`** — typically MD5/SHA of a normalised email, or a keyed hash of an internal user id (better for privacy than raw email hashes on shared infrastructure).
- **`s`** — size preset (allowlisted: 40, 80, 160…).
- **`d`** — default policy when missing: solid colour, generated identicon/mystery-person, or redirect to a global default asset.

The browser and CDN treat this like any other immutable-ish static file. Comment threads, leaderboards, and emails reference the URL without calling your identity API.

## Upload and publish path

<Steps>
  <Step title="User uploads a photo">
    Prefer direct-to-object-storage (13.01) into a private incoming key.
  </Step>
  <Step title="Process fixed presets">
    Eager-generate square crops at the allowlisted sizes (and maybe WebP+JPEG). Avatars are hot and few-variant — a good eager case from 13.02.
  </Step>
  <Step title="Publish under the hash key">
    Write to `avatar/\{hash\}/80.webp` etc., or one master plus CDN presets. Update `avatar_version` if you use versioned URLs.
  </Step>
  <Step title="Invalidate or version">
    Either `?v=\{version\}` on the URL your API returns, or short TTL plus purge. Version query params are the reliable option.
  </Step>
</Steps>

## Defaults and missing users

Default images prevent broken icons for users who never uploaded. Generated identicons also avoid leaking whether an email is registered when the hash is email-based — a privacy footgun of naive "404 vs 200" behaviour on email-hash URLs. Prefer:

- Always 200 with a default image, or
- Hash internal ids that are not guessable from email, and rate-limit lookup APIs separately.

## Privacy and abuse

| Risk | Mitigation |
| --- | --- |
| Email → hash rainbow tables | Prefer internal id hashing; salt if the CDN is shared; treat email hashes as personal data |
| Hotlinking / scrapers | Signed URLs, referrer policy, or accept that public avatars are public |
| NSFW uploads | Moderation queue before publish; revert to default on strike |
| Tracking pixels via avatar | Separate avatar CDN host; careful cookie policy |

<Callout type="note">
If your API already returns user objects with a CDN avatar URL, HTML never needs a secondary identity round trip. That single field is the integration surface — keep it stable, versioned, and size-agnostic (`s` param or srcset).
</Callout>

## In an interview

Describe opaque hash (or user-id) URLs on a CDN, eager small presets, version params on change, and safe defaults that do not leak account existence. Mention direct upload + processing. Keep it short — avatar services are an application of 13.01/13.02, not a separate storage invention.
