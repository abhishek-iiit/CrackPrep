## Business logic that imports a SQL driver is business logic you cannot test alone

Put a query directly inside a service method — a `SELECT` against pending orders for a user sitting next to the discount calculation that uses its result — and the discount calculation cannot be tested without a live database. Every unit test becomes an integration test: spin up a database, seed rows, tear it down, repeat for every case. Multiply that by a test suite with thousands of cases and the suite's runtime becomes the bottleneck on how fast anyone gets feedback on a change.

The repository pattern draws a boundary at exactly that seam. Business logic talks to an interface — `OrderRepository.findPendingByUser(userId)` — and something else, the concrete repository implementation, is the only code that knows it is talking to Postgres, or DynamoDB, or a REST API wrapping a legacy system. The business logic imports the interface, not the driver.

```text
interface OrderRepository {
  findPendingByUser(userId): Order[]
  save(order): void
}

class PostgresOrderRepository implements OrderRepository { ... }   // real
class InMemoryOrderRepository implements OrderRepository { ... }   // test double
```

A unit test for the discount calculation can hand it an `InMemoryOrderRepository` seeded with three orders in a map, no database involved, running in microseconds instead of milliseconds against a real connection. That is the pattern's actual payoff, and it is worth being precise about it: the payoff is testability first. "Swap the database later" is the pitch most often given for the pattern, and it is real but overstated — more on that below.

## What the interface has to get right

The interface is a contract, and like any contract it has to match what callers actually need without leaking how the current implementation gets there:

- **Methods should read like domain operations, not like SQL translated into function names.** `findPendingByUser` describes what the business needs; a name built from a chain of field-equals-value clauses describes a `WHERE` clause with the SQL filed off. The second version has already leaked the query builder into the interface.
- **Return domain objects, not database rows.** A repository that returns a raw row forces every caller to know the column names and their types, which is exactly the coupling the pattern exists to remove.
- **Writes that must be atomic together need a unit of work, not two repository calls.** If saving an order and decrementing inventory must succeed or fail together, calling one repository's save and then another repository's decrement gives you two separate commits with a window between them where one can succeed and the other fail. A unit of work — a single object that tracks changes across repositories and commits them in one transaction — is the piece that actually restores atomicity; the repository pattern alone does not provide it.

<Callout type="gotcha">
The interface tends to leak in the direction of whatever the concrete implementation makes easy, not what the domain needs. A method that fetches a user's orders and, for each one, calls a line-item repository by order id looks clean at the call site and hides an N+1 query: one query for the orders, then one more per order for its line items. The repository pattern makes this easier to hide, not harder to cause — the abstraction has no opinion about how many queries its implementation issues, so N+1 problems still have to be caught by reading what the concrete class actually does, not by trusting the interface.
</Callout>

## What it costs, and what it doesn't buy

The pitch "swap Postgres for DynamoDB without touching business logic" survives contact with reality only partway. The method signatures can stay the same. What does not transparently carry over: a relational store gives you ad-hoc joins and transactions across arbitrary rows for free, and a key-value or document store generally does not — a repository method that did a three-table join under a relational engine has to become several calls and an in-memory join under a key-value store, or a denormalized read model has to exist specifically to answer that query. The interface hides the syntax difference. It cannot hide a difference in what the underlying store is actually capable of doing efficiently, and pretending otherwise produces a repository implementation that quietly does the join in application code, one row at a time, which is often slower than what it replaced.

The other cost is boilerplate for cases that do not need it. A small CRUD service with one database it has no plan to ever change gets an interface, an implementation, and a test double for logic that could have called the ORM directly with no loss of testability, if the test suite was always going to run against a real test database anyway. The pattern earns its cost when there is real logic to isolate from persistence, or a genuine multi-backend requirement — not by default on every table.

## In an interview

This comes up less as a scale question and more as a "how would you structure the code" follow-up once the data model is settled. A concrete answer names the actual boundary: "The order service depends on an `OrderRepository` interface, not on the ORM directly, so the discount logic can be unit-tested against an in-memory fake. Writes to orders and inventory that need to be atomic go through a single unit of work rather than two separate repository calls." That sentence shows you know the pattern buys testability, and that it does not by itself buy transactional safety across repositories — a distinction interviewers often probe for specifically.

If asked about swapping databases, give the honest version: the interface hides syntax, not capability — moving from a relational store to a key-value store changes what queries are cheap, and the repository implementation has to change shape, not just its internals, to keep serving the same interface efficiently.
