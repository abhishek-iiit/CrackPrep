## "It should be fast and reliable" is not a requirement yet

01.01 Requirements Clarification draws the line between what a system does and how well it must do it. This lesson is what belongs on the second list, and why leaving it blank is not neutral. "A user places an order" is a functional requirement — concrete, testable, you can name the API call. "It should be fast and reliable" sounds like it belongs next to it, but it has no unit, no threshold, and no way to fail a test. It is a slogan wearing the shape of a requirement.

An unstated non-functional requirement does not stay unstated. It gets a value anyway, chosen by whatever default happens to be lying around. Nobody sets a request timeout, so the timeout is however long the OS lets a socket sit idle before the client gives up — minutes, not seconds. Nobody says how many copies a write needs before it's safe, so the answer is whatever replication factor the datastore ships with out of the box. Non-functional requirements that are never asked for are not requirements that don't exist; they are requirements resolved by someone else's default, discovered later, usually in production.

## The categories worth naming out loud

Each of these should end as a sentence with a number in it, not an adjective. The filter from 01.01 still applies: if you can't write a test that passes or fails, the threshold is still missing.

| Category | The question to ask | A testable target |
| --- | --- | --- |
| Latency | How long can one request take before a user notices? | "reads at p99 under 200 ms" |
| Throughput | How many operations per second at peak, not on average? | "12k writes/s at peak" — see 01.06 Back-Of-The-Envelope Capacity Planning for how that number gets derived |
| Availability | What fraction of requests must get an answer at all? | "99.9% of requests succeed, measured monthly" — see 14.02 SLOs And Error Budgets for turning that into something a team gets paged against |
| Durability | Once a write is acknowledged, can it ever be lost? | "at most one write in a billion lost per year" |
| Consistency | Can two concurrent reads of the same data disagree, and for how long? | "reads may lag writes by up to 5 seconds" |
| Scalability | Does this have to grow without a rewrite, and by how much? | "10x current traffic within two years, same architecture" |
| Fault tolerance | What can fail without the system going down? | "any single node failure is invisible to users" |
| Security & compliance | What data needs encryption, isolation, or a retention rule? | "PII encrypted at rest; deleted within 30 days of a request" |
| Cost | What is the ceiling this design must fit under? | "under $0.001 of infra cost per request served" |

## They price against each other, not in isolation

None of these are free knobs you turn up independently. Stronger consistency usually costs latency, because answering "the latest value, guaranteed" requires either routing through a single source of truth or coordinating between replicas before responding — 01.05 Availability Durability Consistency And Cost and 06.04 CAP And PACELC both work through the shape of that specific trade. Higher durability costs write latency and money, because an acknowledgment has to wait for more independent copies of the data to exist somewhere durable before it can be sent. And every one of these costs against the last row in the table: five nines of availability layered onto a five-second consistency window in the same system is not five times more expensive than either alone — it's often an order of magnitude more, because the machinery built to guarantee one interacts with the machinery built to guarantee the other.

The value of pinning a number down is that it decides architecture, not detail. Take a payment endpoint with the functional requirement "charge the customer's card." The moment a client is allowed to retry that request — because the network timed out, not because it failed — an implicit non-functional requirement appears: must a retried request charge the card twice? If the answer is no, the real requirement is "at most one charge per logical attempt, even under retries," and that pushes the design toward an idempotency key (02.09 Retries Timeouts And Idempotency) before it pushes toward any particular database. The functional requirement never changed. The number attached to it decided the architecture.

<Callout type="gotcha">
A default is still a decision, just one nobody inspected. Most ORMs ship with a default transaction isolation level, most HTTP clients ship with a default timeout, most message brokers ship with "at least once" delivery unless told otherwise. None of these defaults are wrong by themselves — they're wrong when nobody checked whether they match the actual requirement, and the gap surfaces as a duplicate charge, or a request that hangs for ninety seconds instead of failing fast at one.
</Callout>

## In an interview

State the non-functional targets as soon as the functional scope is agreed, before drawing anything — ask for latency, availability, consistency, and cost by name, the same way you'd ask for the four numbers in 01.01. When an architecture clearly favors one axis over another, say which one you're sacrificing before you're asked: "I'm choosing to serve this from a cache that can be a few seconds stale, which means I'm giving up strict consistency for latency and cost" reads as a decision. Waiting for the interviewer to ask "what about consistency" and only then admitting it reads as an omission you were hoping nobody would notice.
