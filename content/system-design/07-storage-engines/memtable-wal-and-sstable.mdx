## Three structures, one contract: durable now, sorted later

07.09 LSM Tree Storage Engine gives the whole engine. This lesson opens the three pieces every write actually touches: the **memtable**, the **WAL**, and the **SSTable**. Miss the job of any one of them and the design stops making sense — people say "LSM" and then propose durability from the memtable alone, or sorted files without a recovery log, or a mutable on-disk table that quietly becomes a B-tree.

The contract split is sharp. The memtable makes recent writes fast and ordered in memory. The WAL makes acknowledged writes survive a crash. The SSTable makes older data durable, immutable, and searchable without holding every key in RAM. Compaction (07.12) is what happens *between* SSTables after they exist; it is not a fourth structure on the write path of a single put.

## Memtable: sorted, mutable, and capped

The memtable is an in-memory sorted map — usually a skip list, sometimes a balanced tree or a concurrent variant of either — holding the newest key versions. It is sorted for two reasons that are both load-bearing: a flush can emit keys in order in one sequential pass, and a range scan can merge the memtable with on-disk iterators without an extra sort.

It is also **size-capped**. When it hits its bound (a memory budget measured in megabytes to low hundreds of megabytes in typical deployments — order-of-magnitude, depends on heap and write rate), the engine freezes it, installs a fresh empty memtable for new writers, and schedules the frozen one for flush. Writers never wait on the flush itself if the pipeline is healthy; they wait only if too many frozen tables are already queued and memory pressure forces backpressure.

Updates do not overwrite entries in place inside the memtable either. A new put for an existing key is a new entry with a higher sequence number sitting beside the old one (or replacing it inside the structure while retaining sequence order for snapshots). That keeps the whole engine append-oriented even before anything hits disk.

## WAL: durability that does not depend on the memtable

The memtable is volatile. An acknowledged write that lived only there is gone after power loss. So every durable write is appended to a **write-ahead log** first — or in the same critical section, depending on the engine — as a serialized record with key, value or tombstone, and sequence number. The fsync on that append (often group-committed across writers) is the durability event. See 03.08 Database WAL And Recovery for the general recovery mechanics; the LSM twist is that the WAL's lifetime is tied to memtable flush, not to page flush.

<Steps>
  <Step title="Append to the WAL and fsync on the durability policy">
    Group commit batches many logical writes behind one fsync so the durable rate tracks fsync throughput times batch size. This is usually the only synchronous device touch on the put path.
  </Step>
  <Step title="Insert into the active memtable">
    Sorted in-memory insert. The write is now visible to readers that see this sequence number.
  </Step>
  <Step title="Acknowledge the client">
    Durable because of the WAL; visible because of the memtable. No SSTable has been written yet.
  </Step>
  <Step title="Freeze and flush when the memtable fills">
    The frozen memtable is written out as one SSTable in key order. When that file is fsynced and referenced from the manifest, the WAL segments that only covered those writes can be deleted or recycled — the SSTable is now the durable copy.
  </Step>
  <Step title="On crash, replay any WAL still needed">
    Restart rebuilds memtables by replaying remaining WAL records, then resumes. Replay cost is proportional to data written since the last successful flush, which is why oversized memtables mean longer recovery as well as larger flushes.
  </Step>
</Steps>

<Callout type="gotcha">
If you size the memtable for write throughput alone — huge tables, rare flushes — you also size crash recovery and the amount of data that must be rewritten if a flush fails. If you size it tiny, you flood L0 with small SSTables and amplify compaction and read candidate counts. Memtable size is not a free knob for "more write buffer"; it is a three-way trade among memory, recovery time, and flush/compaction shape.
</Callout>

## SSTable: immutable sorted string table

An SSTable (sorted string table) is a file of key/value entries in key order, plus auxiliary blocks that make point lookups cheap, written once and never modified. Immutability is the point — 07.06 Immutable Versioned Data Files — because it lets the engine treat the file as a stable unit for caching, checksumming, Bloom filters, and compaction inputs.

A typical layout:

```text
SSTable  (written once, in key order, never modified)

  [ data block 0 ] [ data block 1 ] ... [ data block N ]
  [ filter block ]    Bloom filter over keys in this file
  [ index block ]     sparse index: first key of block → offset
  [ footer ]          offsets to the above, checksums, seq range
```

**Data blocks** hold the actual keys and values (often prefix-compressed within a block). Block size is a tuning knob — larger blocks compress better and shrink the index; every point read that hits must fetch a whole block.

**Sparse index** stores one entry per data block, not per key: the first key of the block and the file offset. Binary search over the sparse index (kept in memory or in a cached index block) yields at most one data block that could contain the target key. That is how an SSTable delivers "one block read on a hit" without a Bitcask-sized exact index. 07.11 LSM Read Path Bloom And Sparse Index pairs this with the filter.

**Bloom filter** answers "definitely not in this file" in memory for point lookups. Built at flush time from the known key set — exact `n`, no deletes needed later because the file will not change (04.13 Bloom Filters).

**Footer** anchors everything: offsets to index and filter, checksums, smallest/largest key, sequence number range. The manifest points at the file; the footer lets a reader map the file without scanning it.

## How the three meet on a single write

Put the pieces on one timeline for one durable put that later becomes an L0 file:

1. WAL append (+ group fsync) — durable.
2. Memtable insert — visible.
3. Ack.
4. Later: memtable freeze → sequential write of data blocks, filter, sparse index, footer → fsync → manifest edit → WAL reclaim.

Nothing in steps 1–3 depended on how many SSTables already exist. That is why LSM write latency stays mostly independent of dataset size until compaction or L0 backpressure intervenes — those are separate stages with their own failure modes (07.09, 07.12).

## Flush versus compaction

Flush and compaction are easy to conflate and important to separate.

| | Flush | Compaction |
| --- | --- | --- |
| Input | One frozen memtable | Existing SSTables (often across levels) |
| Output | One new L0 SSTable | New SSTables at a target level |
| Merges with peers? | No — that is why L0 ranges overlap | Yes — merge-sort, drop obsolete versions |
| On the latency path of a put? | Only if the flush queue backs up | Only if debt triggers write stall |
| Purpose | Bound memory; move durability off the WAL | Bound read amplification and space |

Flush turns memory into an immutable file as cheaply as possible. Compaction turns many files into fewer, cleaner files. Engines that "compact on flush" are still doing two jobs; they have just scheduled them together.

## In an interview

Name the three roles in one breath: "Memtable for sorted recent writes in memory, WAL so those writes survive a crash, SSTable as the immutable sorted file a flush produces — and nothing updates an SSTable in place." Be ready to explain why the WAL can be deleted after flush (the SSTable superseded it for durability) and why L0 files overlap (flush does not merge). If asked about file internals, say sparse index per block plus Bloom filter — one block read on a hit, near-zero I/O on a miss when the filter says no — and point to 07.11 for the read-path walk.
