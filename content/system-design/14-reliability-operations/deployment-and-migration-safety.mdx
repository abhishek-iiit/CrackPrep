## The dangerous deploy is the one you cannot undo

Most production incidents still involve a change — a new binary, a config flag, a schema edit, a traffic shift. Deployment safety is the set of practices that make change *reversible*, *observable*, and *incremental* so a bad diff burns a slice of the error budget (14.02) instead of the whole month. Migration safety is the same idea applied when the change cannot be a pure rollback because data or contracts moved; 14.05 Database Migration Safety goes deep on schema mechanics — this lesson is the broader release and cutover discipline.

A "deploy" that is only `ssh` and hope is not a strategy. Neither is a pipeline that is green while your only verification is "the process started."

## Incremental delivery patterns

| Pattern | How it limits blast radius | Rollback story |
| --- | --- | --- |
| Rolling deploy | Replace instances in small batches | Redeploy previous artifact; in-flight mixed versions must be compatible |
| Canary | Tiny % of traffic or one cell first | Instant traffic shift off canary if SLIs burn |
| Blue/green | Two full environments; flip the router | Flip back; cost is double capacity during the window |
| Feature flags | Code dark until flag on; progressive expose | Turn flag off without redeploying |
| Shadow / dark launch | New path gets duplicated traffic, response ignored | No user impact; compare diffs offline |

Canaries need **automated** promotion criteria — error rate, latency, key business metrics — not a human staring at a graph for thirty seconds. Humans approve exceptions; machines catch the obvious.

<Callout type="gotcha">
Forward-incompatible APIs between services during a rolling deploy are a classic silent outage: old callers hit new callees (or the reverse) and fail only on some percentage of pods. Require proto/JSON compatibility across at least one version skew, or deploy consumers before producers for additive changes and the reverse for removals.
</Callout>

## Expand, migrate, contract

When the change is structural — dual writes, a new table, a new service owning a path — use the expand/contract sequence rather than a big-bang cutover:

<Steps>
  <Step title="Expand">
    Deploy code that can read (and optionally write) both old and new representations. Old path remains authoritative.
  </Step>
  <Step title="Migrate">
    Backfill data, dual-write, or shadow-read the new path. Verify with metrics and spot checks until confidence is high.
  </Step>
  <Step title="Shift">
    Move read traffic gradually (14.06 Parallel Monolith Read Drain is one concrete form). Watch SLIs and correctness diffs.
  </Step>
  <Step title="Contract">
    Remove dual paths and old code only when the new path has owned traffic long enough that rollback would reintroduce the old system deliberately, not as a panic.
  </Step>
</Steps>

Feature flags make expand/contract operable at runtime: a flag can choose old versus new read path without a redeploy. Flags that live forever become a combinatorial test nightmare — treat cleanup as part of the migration, not optional hygiene.

## Config and data are deploys too

A config-service change or a price-table push can page as hard as a binary. Apply the same rules: canary config, versioned config, instant revert. Schema and backfill jobs get their own review — locking migrations, full-table rewrites at peak, and irreversible data transforms are how "maintenance windows" become incidents (14.05).

Health checks should fail closed on dependencies you need, but not so eagerly that a brief blip drains the whole cluster into a crash loop. Separate *liveness* (restart me) from *readiness* (leave me in the pool).

<Tradeoff

## In an interview

Talk about changing production as a controlled experiment: "Canary a small fraction, gate on SLIs, rollback by traffic shift or flag; for data changes use expand/migrate/contract so mixed versions stay safe." Name version skew between services as a failure mode. If asked about database specifics, point to online-safe schema steps and link the idea to 14.05 without drowning in DDL.
