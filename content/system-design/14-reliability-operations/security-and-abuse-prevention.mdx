## Your public surface is a shared resource attackers optimize against

System design that ignores abuse assumes clients are polite and credentials stay secret. Real systems face credential stuffing, scraping, spam account creation, card testing, content abuse, and DDoS — often automated, often indistinguishable from "enthusiastic" users until you look at graphs. Security and abuse prevention is the set of controls that keep unauthorized action expensive and automated abuse unprofitable, without turning every login into a CAPTCHA farm.

Rate limiting (14.13, 14.14) is one tool. It is not a security strategy by itself. Authn, authz, audit, fraud signals, and operational response close the loop.

## Boundaries first

- **Authenticate** what you can; treat anonymous endpoints as hostile by default (stricter quotas, proof-of-work, or disable expensive queries).
- **Authorize** on every sensitive action with server-side checks — never trust client-supplied roles, prices, or user ids.
- **Least privilege** for service credentials; blast radius of a leaked worker token should not be "entire datastore."
- **Encrypt in transit everywhere**; encrypt sensitive fields at rest when breach impact demands it.
- **Audit** security-relevant events (login failures, permission denials, admin actions) with retention suited to investigation (14.11).

Signed URLs and DRM (13.07) are media-specific authorization at the edge — the same idea as capability tokens generally.

## Abuse as a feedback loop

Attackers probe, you block a signal, they rotate the signal. Durable defenses stack layers that raise cost at each step:

| Layer | Examples | Limit |
| --- | --- | --- |
| Network / edge | WAF, IP reputation, volumetric DDoS scrubbing | Spoofing, distributed botnets, false positives on NATs |
| Protocol / API | Auth required, schema validation, size limits, load shedding (02.13) | Authenticated abuse |
| Identity | MFA, device binding, step-up auth on risky actions | Account takeover after session theft |
| Velocity / rate limits | Per IP, account, device, API key (14.13) | Key choice errors punish NATs or miss distributed bots |
| Risk scoring | Fraud models, graph of linked accounts, payment signals | Needs data, creates bias/privacy tensions |
| Human ops | Trust & safety queues, takedowns | Does not scale alone; needed for novel attacks |

<Steps>
  <Step title="Inventory expensive and dangerous operations">
    Login, password reset, OTP send, search, export, payment authorize, content post, URL expand — anything costly or harmful when automated.
  </Step>
  <Step title="Attach controls proportional to risk">
    Cheap GETs might get IP rate limits; OTP send gets per-account and per-destination limits plus anomaly detection; admin APIs get MFA and allowlists.
  </Step>
  <Step title="Instrument attempts, not only successes">
    Failed logins, `429`s, CAPTCHA serves, and fraud declines are first-class metrics. Silent success-only metrics miss the war.
  </Step>
  <Step title="Plan the false-positive path">
    Legitimate users hit blocks. Support runbooks, graduated challenges (step-up MFA before hard ban), and fast unblocks matter as much as the block itself.
  </Step>
</Steps>

<Callout type="gotcha">
IP-only blocking on mobile and university NATs collapses thousands of users into one key — you will rate-limit a campus to protect yourself from one scraper. Combine keys (14.13) and prefer account- and device-scoped limits once identity exists.
</Callout>

## Fail closed on authz, carefully on availability

Authorization checks should fail closed: if the policy service is down, do not grant admin. Availability controls are subtler — failing closed on every dependency can amplify an outage into a total lockout. Distinguish **security decisions** (fail closed) from **enrichment** (risk score timeout → treat as medium risk + step-up, not as allow-all).

Secrets belong in a manager, not in images. Rotate. Assume leak. SSRF, path traversal, and injectible query surfaces are implementation bugs that architecture reviews should still call out when drawing upload or URL-fetch features.

## In an interview

Refuse the "we will add a firewall" shrug. Inventory dangerous operations, put authz on the server, rate-limit with thoughtful keys, and add step-up challenges for high risk. Mention false positives and fail-closed authz. Tie volumetric overload to load shedding and rate limits as related but distinct. Abuse is an expected workload, not an edge case.
