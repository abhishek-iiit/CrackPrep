## Sharing machines is easy; sharing fate is the part you design

Multi-tenant systems serve many customers (tenants) from shared software and usually shared infrastructure. The business win is density and operational leverage. The engineering problem is **isolation**: one tenant's traffic spike, buggy integration, or compromised account should not exhaust the database, read another tenant's rows, or wipe another tenant's data. Tenancy is a reliability and security design (14.12), not only a `tenant_id` column.

## Isolation spectrum

| Model | How tenants separate | Density | Isolation |
| --- | --- | --- | --- |
| Shared schema (row-level) | `tenant_id` on rows; shared DB | Highest | Weakest if queries miss the predicate |
| Shared DB, separate schemas | Schema per tenant | High | Better DDL isolation; operational overhead |
| Database per tenant | Separate DB instances | Medium | Strong data isolation; costly at thousands of tenants |
| Stack per tenant (silo) | Separate deploys/accounts | Lowest | Strongest; essentially managed single-tenant |

Most SaaS starts row-level with strict discipline, then silos enterprise customers who pay for stronger isolation or have residency needs. Hybrid is normal: pool for the many, dedicated for the few.

## The `tenant_id` invariant

Every query, cache key, queue message, blob prefix, and log line that can carry data must be tenant-scoped. A single missing `WHERE tenant_id = ?` is a data leak. Defenses:

- **Forced predicates** — ORM filters, middleware that injects tenant from the authenticated principal (never from a client-supplied header alone).
- **Separate encryption keys per tenant** when crypto-isolation matters.
- **Prefix object keys** with tenant id; IAM policies that cannot read across prefixes.
- **Tests** that attempt cross-tenant reads in CI.

Token and session design must bind tenant context: a user in tenant A is not authenticated for tenant B's admin API just because the user id string collides.

## Noisy neighbors

Shared CPU, connection pools, and disk IO mean one analytics-heavy tenant can starve others. Controls stack with rate limits (14.13):

- Per-tenant request and concurrency quotas.
- Separate pools or admission control for heavy report queries.
- Storage and API quotas with soft then hard ceilings.
- Noisy-neighbor detection (tenant-level USE metrics) and automatic throttle.

<Callout type="warn">
A global connection pool with no per-tenant cap lets one tenant hold every Postgres connection — the outage presents as "database down" for everyone while the graph shows one tenant's connection count equal to `max_connections`. Cap per tenant and shed (02.13) the offender.
</Callout>

## Tenancy in async and analytics paths

Workers must read `tenant_id` from the message and apply the same authz when processing. Fan-out jobs should not run one tenant's export with another's credentials. Analytics pipelines need tenant-aware partitioning or separate warehouses for high-tier customers — otherwise retention and erasure (14.10, 14.11) cannot run per tenant, and one customer's PII infects shared aggregates.

Migrations (14.05) on shared schemas affect all tenants at once — expand/contract discipline and canaries by tenant cohort (ramp a percentage of tenants) reduce blast radius.

| Concern | Shared-schema approach | Silo approach |
| --- | --- | --- |
| Noisy neighbor | Quotas, pools, QoS | Natural isolation |
| Compliance residency | Row + region pinning hard; often need silo | Deploy silo in-region |
| Per-tenant custom schema | Painful | Natural |
| Ops cost at 10k tenants | Favored | Usually impossible without automation |

## In an interview

Define tenancy as shared infrastructure with isolation goals, pick a model (usually shared schema + quotas, silo for enterprise), and hammer the invariant: "tenant context comes from the credential, every data access is predicated, every cache key and blob is prefixed, workers carry tenant id." Mention noisy-neighbor connection caps and per-tenant rate limits. If asked about GDPR erasure, say per-tenant deletion must reach shared analytics too.
