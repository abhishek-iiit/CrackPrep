## Two different questions, easy to answer with one box

Once a service has more than one replica, something has to decide which replica answers a given request — that's a load balancer's entire job, and it's a narrow one. Once a system has more than one service, a different set of questions shows up at the edge: which service does this request even belong to, is the caller allowed to make it at all, and does the request need to be reshaped before anything downstream can understand it. That's an API gateway's job, and it's a broader one. At small scale it's tempting, and often fine, to answer both with the same box. The confusion starts when the system outgrows that and "load balancer" and "API gateway" keep getting used interchangeably for a component that's actually doing gateway work.

## What a load balancer alone does

A load balancer distributes traffic across a pool of replicas that all serve the *same* logical service — it doesn't know or care what the request means, only whether a given backend is healthy and which algorithm should pick it. 02.06 Load Balancers covers the algorithms and health-check mechanics; what matters here is the scope: one balancer, one backend pool, one routing question — which instance.

Some load balancers work at L4 (TCP/UDP), forwarding packets by IP and port without ever parsing the request inside them; others work at L7, parsing HTTP far enough to route on a path or a header. L7 routing by path can look like gateway behavior, and the line genuinely blurs here — but a load balancer routing `/orders` and `/users` to different pools is still only choosing among servers based on what it read, not enforcing who's allowed to read it, reshaping the payload, or rate-limiting by caller identity.

## What an API gateway adds

A gateway sits in front of many services, not one pool, and takes on the concerns that don't belong to any single service's replicas:

- **Authentication and authorization**, enforced once at the edge instead of reimplemented in every service behind it.
- **Rate limiting per client**, so one caller can't starve every other caller of a shared backend — 14.13 Rate Limiter Placement And Keys and 14.14 Sliding Window Rate Limiter cover the mechanism.
- **Routing by path or host to entirely different backend services**, not just replicas of one service.
- **Request and response transformation** — reshaping a payload, aggregating a client's request across several backend calls into one round trip, or translating protocols, such as terminating a public REST call and issuing an internal gRPC call.
- **TLS termination and centralized logging**, so every request crossing the edge is observable in one place instead of scattered across every service's own logs.

A request in a system with both usually crosses the gateway first — authenticate, rate-limit, decide which service this is for — and only then reaches that service's own load balancer, which picks the specific healthy replica. "Which service" and "which instance" are different decisions, made by different components, and collapsing them into one box is a simplification that works until the number of services or the need for per-caller policy outgrows it.

<Callout type="warn">
A gateway that sits in front of every service becomes a single point of failure for the entire system, not just one service — an outage there takes down everything behind it, unlike a load balancer outage, which only takes down the one pool it fronts. Treat it with the redundancy of critical shared infrastructure: multiple instances behind its own load balancing, and a health story that gets tested, not assumed.
</Callout>

## In an interview

Name the split explicitly rather than drawing one box labeled "LB/gateway": "the gateway decides which service and whether the caller's allowed to ask; the load balancer behind it decides which healthy replica of that service answers." If asked when you'd introduce a gateway, tie it to 01.09 Monolith Vs Microservices — a gateway earns its place at roughly the same point splitting into services does, because it's the component that keeps cross-cutting concerns from being reimplemented once per service. Say out loud that it becomes a single point of failure the moment it sits in front of everything, so it needs its own redundancy story, not just the services behind it.
