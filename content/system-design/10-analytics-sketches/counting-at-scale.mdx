## A number that everyone wants to change at once

Somewhere behind "1.2M views" or "48 likes" is usually one row: `UPDATE posts SET view_count = view_count + 1 WHERE id = ?`. At ten writes a second this is invisible — the database serializes them, each one takes a fraction of a millisecond, and nobody notices. At ten thousand writes a second against the same row, every one of those writes is now waiting behind the one before it, because each has to lock the row, read the current value, add one, and write it back. The database is not slow. It is correct, and correctness on a single row is the bottleneck.

This is a different problem from the query being slow. `SELECT COUNT(*) FROM likes WHERE post_id = ?` has its own cost — it scans or index-scans every matching row, so cost grows with the table rather than staying constant — but that is a read-side cost a cache can absorb. A hot counter row is a write-side cost, and a cache does not help a write: every increment still has to land somewhere, in order, without losing one.

The two failure modes look different in production, too. The `COUNT(*)` query shows up as a slow endpoint, easy to spot in a trace. The hot row shows up as lock wait time that appears in no single query's execution plan — it presents as throughput that flatlines no matter how many application servers you add, because they are all still waiting on one row on one database instance.

## Three ways out, and what each one gives up

Every fix for a hot counter trades exactness or freshness for throughput. There is no version that keeps all three.

- **Batch the increments.** Instead of writing to the database on every event, accumulate the count in memory — in the request-handling process, or in a fast in-memory store like Redis — and flush a single `UPDATE ... SET count = count + N` every second or every few hundred events. This turns thousands of row writes into one, at the cost of a small window where the durable count lags reality. 02.10 Batching covers the general pattern and its failure mode: a crash between the increment and the flush loses whatever was buffered and never written through.
- **Shard the counter.** Split one row into many — `counter_id = post_id:0` through `post_id:15` — and increment a randomly chosen shard on write, summing all shards on read. No single row absorbs the full write rate; contention drops by roughly a factor of the shard count. The cost lands on reads, which now touch N rows instead of one, and on keys hot enough that even a sharded write path can saturate — the general problem is 04.06 Hot Partitions, and 04.05 Sharding And Partitioning covers picking a shard key.
- **Stop counting exactly.** If the product only needs "48" to become "1.2K" rather than a number accurate to the unit, an approximate structure that tolerates concurrent, lossy updates can absorb far more write volume than an exact counter — this is the family of sketches the rest of this module covers, starting with 10.04 HyperLogLog Cardinality Estimation for distinct counts and 10.05 Mergeable Sketches For Analytics for why these structures combine cleanly across shards.

None of these is free, and in practice they compose: a production view counter is usually sharded *and* batched, with an approximate display value shown to users while an exact reconciliation runs in the background. 10.02 View Counting At Scale and 10.03 Impression Counting System Design work through two concrete versions of that combination.

<Callout type="note">
The three fixes solve different bottlenecks. Batching reduces write *frequency*; sharding reduces write *contention*; approximation reduces write *precision*. A system with a contention problem that only batches will still serialize on the flush — batching a hot row just makes it a slightly-less-hot row that saturates a little later.
</Callout>

## In an interview

Name the bottleneck before you are asked to explain it: "A naive counter is one row that every write has to lock, so throughput is capped by however fast that one row can be updated in sequence, not by how many application servers I add." Then pick a fix that matches the actual requirement — batching if the count just needs to catch up periodically, sharding if writes are the bottleneck and reads can afford to fan out, approximation if the product genuinely does not need an exact number. Naming the tradeoff you are accepting — staleness, extra read cost, or precision — is what shows you understand this is a substitution, not a fix with no cost.
