## Global analytics without a global stream

Once traffic is sharded — by user id, by region, by Kafka partition — every interesting aggregate is split across machines. Exact answers then require either shipping every event to one reducer or maintaining a gigantic cross-shard key space. Both fight the reason you sharded in the first place.

Mergeable sketches attack a narrower goal: keep a small summary on each shard, and define an associative combine operation so that `merge(sketch(A), sketch(B))` equals (or closely approximates) `sketch(A ∪ B)` without ever seeing the raw union. If the combine is also commutative and cheap, any reduce tree works — pairs of pods, then racks, then regions — and the final sketch is indifferent to the tree shape.

That property is not automatic. A naive hash map of exact counters merges, but the merged map is as large as the union of keys. A sketch earns the word mergeable when the merged state stays the same fixed size as either parent.

## What "merge" means for the common sketches

| Sketch | Merge operation | Identical parameters required | Extra error from merge? |
| --- | --- | --- | --- |
| HyperLogLog — 10.04 | Per-register maximum | Same `m`, same hash | No beyond each side's own error |
| Count-Min Sketch — 10.08 | Elementwise counter sum | Same `w`, `d`, same hashes | No beyond existing collision error |
| Bloom filter — 04.13 | Bitwise OR | Same `m`, `k`, same hashes | False-positive rate can only worsen toward saturation |
| t-digest — 10.11 | Concatenate centroids, recompress | Compatible compression | Small additional approximation |
| Exact hash map | Key-wise sum / union | None | None, but size grows with union |

The first three are the workhorses of sharded product analytics: unique counts, approximate frequencies, and membership. Reservoir samples (10.10) are trickier — merging two equal-probability samples of size `k` is not as simple as concatenation, and naive concat biases toward whichever stream was larger unless you reweight. Prefer structures whose algebra is documented before you bet a pipeline on ad-hoc merges.

<Callout type="gotcha">
Merging sketches built with different dimensions or different hash seeds is undefined. The cells do not line up. Teams discover this when one service deploys a "better" HLL precision and the global reduce starts mixing 12-bit and 14-bit register files — the merge either fails loudly or silently produces nonsense. Version the sketch parameters next to the data, the way you version event schemas.
</Callout>

## How a production reduce usually looks

<Steps>
  <Step title="Emit sketch updates on the hot path, not raw fan-in to analytics">
    Each ingest worker maintains sketches for the dimensions it owns — HLL for unique users per day, CMS for query frequencies, maybe a Bloom filter for "seen event ids" in a window. Updates stay local to the worker's memory.
  </Step>
  <Step title="Flush sketches on a time or size boundary">
    Every minute, or when a bucket closes, serialize the sketch bytes to object storage or a compact topic. The payload is kilobytes to low megabytes, not the raw event volume for that minute.
  </Step>
  <Step title="Reduce with the sketch's merge, in any associative order">
    A job loads all shard sketches for the same time bucket and parameters, folds them with max/sum/OR, and writes one global sketch (or one sketch per business key like `campaign_id`). Partial reduces can run per region first.
  </Step>
  <Step title="Query the merged sketch; keep raw events elsewhere if you need replay">
    Dashboards read the merged artifact. If someone later changes a filter definition, you need raw or lightly filtered events to rebuild — sketches do not resurrect dropped detail. 10.07 Raw Events Vs Derived Analytics is that split.
  </Step>
</Steps>

Mergeability also composes with time. Independent sketches per five-minute bucket merge into an hour; hours merge into a day — as long as the underlying combine is valid for unions of the observed multisets. For Count-Min Sketch, summing bucket sketches estimates counts over the longer window; for HLL, register-wise max estimates distinct over the union (with the usual caveat that distinct over a week is not the sum of daily distincts — merge the HLLs, do not add the estimates).

## When mergeability is the wrong promise

Some analytics questions are not union-friendly. Medians of medians are not medians. Averages need sums and counts carried separately. Top-K lists from two shards are not the global top-K unless you keep enough candidates or use a sketch that supports the query after merge (CMS+heap rebuilt after merge, or a dedicated heavy-hitter structure). Say the algebraic identity out loud before you draw the reduce tree.

  forTitle="Design around mergeable sketches when"

## In an interview

Frame the constraint first: "Events are partitioned across shards, so I will maintain a mergeable sketch per shard and reduce with the sketch algebra — HLL by register max, Count-Min by cell sum — instead of shipping raw events for every dashboard query." Then name the parameter contract (identical size and hashes) and one statistic that must not be merged naively. Follow-ups often ask how daily unique users relate to weekly: explain merging HLLs versus summing daily estimates, which double-counts users seen on multiple days.
