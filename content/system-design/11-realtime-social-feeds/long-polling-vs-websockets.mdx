## Same product feeling, different failure surface

Long polling and WebSockets both aim at "the server tells the client when something happens" without the client guessing on a short timer. In a demo on localhost they look interchangeable. In production they collide with different pieces of the HTTP stack: reverse proxies, cellular NATs, load-balancer idle timeouts, and how much per-client state the server must remember between messages. Choosing between them is less about latency — both can be near event-time — than about which operational hazards you are willing to own.

11.02 Short Poll Vs Long Poll Vs WebSocket places both options in a three-way cost model with short polling. Here the lens is narrower: once short poll is off the table, what actually differs when you run long poll versus WebSockets behind real infrastructure.

## How long poll behaves under the hood

The client sends a GET (or POST) asking for the next event. The server does not answer until:

- an event is ready, or
- a **application timeout** fires (commonly 15–60 seconds), returning empty or a "retry" marker so the client opens a new request immediately.

While waiting, that HTTP request occupies a worker, async handle, or thread — depending on the server model — and every hop in the path must allow the connection to sit idle that long. The moment any hop's idle timeout is *shorter* than the application's hold, the client sees a disconnect or a 502, reconnects, and you have accidental short polling with worse error rates.

State during the hold is usually "this request is subscribed to channel X." When the response flushes, that state ends. The next long poll re-authenticates and re-subscribes. There is no durable session on the wire between holds — only whatever cookie or token the client sends again.

## How WebSockets behave under the hood

The client starts with HTTP, then Upgrade. After the handshake, frames move both ways on one TCP connection. The server keeps **connection-scoped state** for the lifetime of the socket: user identity, subscriptions, last ping, maybe a buffer of undelivered frames. Heartbeats (ping/pong) exist because intermediate devices will kill a quiet TCP flow — often on the order of 30–120 seconds of silence on carrier NATs and some corporate firewalls; treat that as an order-of-magnitude reminder to probe, not a universal constant.

Because the channel is sticky to one backend process (unless you terminate TLS at a layer that understands the protocol and rebalances — rare), scaling out means sticky load balancing or an external pub/sub plane so a write on another node can reach this socket. 11.01 Real-Time Database And WebSocket Scaling is the fleet design; the point here is that WebSocket statefulness is continuous, while long-poll statefulness is per request.

## Proxies, timeouts, and the places they disagree

| Hazard | Long poll | WebSocket |
| --- | --- | --- |
| Proxy idle timeout | Must exceed hold time on every hop (LB, nginx, API gateway, CDN) | Must allow long-lived upgraded connections; idle TCP still needs app-level pings |
| Request timeout budgets | Client, LB, and app each have a max duration — the shortest wins | Handshake is short; afterward budgets are connection lifetime and ping interval |
| Retry semantics | Natural: every response ends the request; client opens another | Must define reconnect, resume, and whether missed events are replayed |
| Auth refresh | Easy to attach a new token on each poll | Must refresh mid-connection or reconnect when the token expires |
| Buffering proxies | Some buffers delay the empty "hold" response until timeout — breaks the pattern | Upgrade failure or websocket-unaware middleboxes force fallback |
| Server resource shape | Many concurrent *in-flight HTTP requests* | Many concurrent *open sockets* with upgrade-specific memory |

<Callout type="warn">
A load balancer configured with a 60 s idle timeout and an app that holds long polls for 55 s looks fine in staging — until p99 event wait is 50 s and a slightly slower auth check pushes the hold past 60 s. Clients get cut, hammer the LB with reconnects, and the on-call dashboard shows a spike in 5xx with no application error. Align hold timeout to something comfortably below the strictest hop (for example hold 25 s if the LB idles at 60 s), and monitor disconnect reasons separately from application empty timeouts.
</Callout>

### Connection state and fan-out

Long poll: fan-out is "complete every held request subscribed to this key." If two polls from the same user race (slow network, double tab), you can deliver twice or have one waiter starve unless you key waiters carefully. WebSocket: fan-out is "write frames to a connection object," and duplicate tabs are duplicate sockets — usually what you want, but presence accounting must count sockets or sessions explicitly.

When a gateway process dies:

- **Long poll** — in-flight holds fail; clients retry within seconds and land on healthy nodes. No sticky map required for correctness, only for warmth of caches.
- **WebSocket** — all sockets on that process drop at once. Clients reconnect with jitter; a thundering herd can overload auth and subscription rebuild. Sticky maps and registries go stale until TTLs expire.

That asymmetry is why some teams keep long poll as a fallback path even after WebSockets ship: same event API, worse efficiency, better behavior through hostile proxies and during partial fleet failures.

## When the latency story is not the differentiator

Both can deliver an event in well under a second after it is published. WebSockets win on overhead when many events arrive per minute per client — no new HTTP headers, no repeated auth middleware, no LB request logs per event. Long poll wins on operational simplicity when events are rare: you do not maintain heartbeat traffic or upgrade-aware infrastructure, and every hop already knows how to reverse-proxy HTTP.

If the client must upload frequently (chat send, cursor moves), WebSockets avoid a second channel of POSTs. If the client mostly receives, long poll is enough until request volume or proxy pain forces the upgrade — or until SSE is a better unidirectional fit (11.04).

## In an interview

Frame it as operations, not fashion: "Both give near-push freshness. Long poll is repeated held HTTP — every proxy timeout must exceed the hold, and each event costs a request. WebSockets are sticky connection state — heartbeats for NATs, sticky LB or a bus for multi-node, reconnect storms on process death." Then pick based on event rate and proxy constraints. Naming idle-timeout mismatch as a failure mode — clients reconnect-looping with 502s — reads as production experience.
