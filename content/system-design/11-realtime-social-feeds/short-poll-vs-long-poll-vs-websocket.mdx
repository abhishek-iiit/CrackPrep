## Freshness has a price tag, and polling is how you see it

Clients do not magically know the server changed. Something has to ask, wait, or stay connected. Short polling, long polling, and WebSockets are the three HTTP-era answers that show up in almost every feed, chat, or notification design. They differ less in "can they deliver an update" — all three can — than in *who pays how often*: request rate, open connections, and end-to-end delay from write to UI. The decision is a cost model with a freshness SLA attached, not a protocol preference.

11.03 Long Polling Vs WebSockets goes deep on connection state, proxies, and timeouts once you have narrowed to those two. 11.04 WebSockets Vs SSE Vs Long Polling adds Server-Sent Events for the unidirectional case. This lesson stays on the three-way fork and the arithmetic that picks a starting point.

## What each one does

**Short poll.** The client issues a normal request on a timer — every 5 s, 30 s, 2 min — and the server answers immediately with the current state or "nothing new." Idle clients still generate traffic. Latency to learn about a change is up to one full interval on average half an interval.

**Long poll.** The client requests; the server *holds* the response until an event arrives or a timeout fires (often 15–60 s). On response or timeout the client immediately opens the next hold. Freshness can be near push, but every delivery or timeout is still a full HTTP request lifecycle — headers, auth check, load-balancer accounting.

**WebSocket.** After an HTTP Upgrade, a bidirectional framed channel stays open. The server pushes when it wants; the client can send without a new handshake. You pay connection state and heartbeats continuously, and you stop paying per-update HTTP overhead.

| | Short poll | Long poll | WebSocket |
| --- | --- | --- | --- |
| Freshness | Bounded by interval | Near event-time (plus hold setup) | Near event-time |
| Idle cost | Request every interval | One held connection + periodic timeout renewals | One connection + heartbeats |
| Burst cost | Same as idle — timer does not care | One request per event (or batch) plus renewals | Frames on the existing socket |
| Server memory | Mostly stateless per request | State for each held request | State for each open socket |
| Infrastructure fit | Every CDN and cache understands GET | Needs long timeouts end-to-end | Needs sticky LB or a fan-out bus (see 11.01) |

## A cost model you can run on a whiteboard

Fix three inputs:

- **C** — concurrent clients interested in updates
- **U** — useful updates per second across those clients (global event rate × average interest, or per-client rate × C)
- **F** — required freshness: maximum acceptable seconds from write to visible update

Then compare order-of-magnitude **request or message rates** (a ballpark to reason with, not a benchmark):

- **Short poll:** roughly `C / interval` requests per second, with `interval ≤ F`. Independent of U. If C = 100,000 and F = 5 s, you need interval ≤ 5 s → ≥ 20,000 empty-ish GETs/s even when U is tiny. Short poll taxes concurrency, not eventfulness.
- **Long poll:** on the order of `U` completions per second when events are sparse, plus `C / timeout` renewals when idle (every held request eventually times out). If events are frequent, completions approach U and renewals drop. If events are rare, you still pay timeout churn.
- **WebSocket:** steady **C** connections; application messages ≈ **U**; plus heartbeat traffic (e.g. C / 30 s). Connection count replaces request count as the scarce resource.

### Worked sketch

100k concurrent clients, each must see a badge update within 3 s. Average useful updates: 500/s globally (many clients share streams; per-client rate is low).

- Short poll at 3 s → ~33k req/s baseline. Mostly 304s or empty payloads. Cheap per request, expensive in aggregate — auth, LB, and app QPS all see that floor.
- Long poll with 30 s timeout → idle renewals ~3.3k req/s, plus ~500 completions/s when events flow. Far fewer requests than short poll; you now hold ~100k concurrent HTTP requests on the servers.
- WebSocket → 100k sockets, ~500 push messages/s, heartbeats ~3k/s. Request QPS collapses; RAM and gateway count rise.

Same freshness target, three different bottlenecks: request throughput, held-request capacity, or connection capacity. Name which resource you have headroom for.

<Callout type="tip">
If the freshness SLA is loose — "within a minute is fine" — short poll with a 30–60 s interval is often the correct answer, especially behind a CDN that can cache a public "latest version" document. Jumping to WebSockets because "realtime sounds better" buys operational surface area for a budget nobody asked for.
</Callout>

## Decision framework

<Steps>
  <Step title="Write the freshness number">
    Maximum seconds from server commit to client UI. Sub-second interactive (typing, games, collab cursors) almost always wants a persistent channel. Multi-second feed badges and "new items available" often do not.
  </Step>
  <Step title="Estimate concurrent waiters vs event rate">
    High C, low U favors long poll or WebSocket over short poll. High U to mostly the same C favors WebSocket so you are not completing an HTTP request per event. Low C makes all three fine — pick the simplest to operate.
  </Step>
  <Step title="Check whether the client must send often">
    Bidirectional chatter (chat send, presence, Cursor moves) tilts to WebSocket so uploads are not separate POSTs. Read-mostly notifications can stay on long poll or, later, SSE (11.04).
  </Step>
  <Step title="Price the idle path">
    Short poll: interval × C forever. Long poll: timeout renewals. WebSocket: heartbeats + RAM. If product usage is mostly idle tabs, short poll with a long interval or visibility-aware pausing (poll only when the tab is focused) can beat a permanent socket farm.
  </Step>
  <Step title="Name the first bottleneck you will hit">
    App request QPS → leave short poll. Held connections through proxies → pressure-test long poll timeouts. Sticky sessions and gateway memory → budget for WebSockets via 11.01. Pick the mechanism whose bottleneck you can actually buy your way out of.
  </Step>
</Steps>

## In an interview

Do not recite definitions. Put numbers on the board: concurrent clients, freshness SLA, updates per second. Show that short poll cost is `C/interval`, long poll blends event completions with timeout renewals, and WebSocket cost is dominated by `C` connections. Then pick one and say what you will monitor — request QPS, held connections, or gateway RAM. Mention that long poll and WebSocket converge operationally once proxies and idle timeouts enter the chat (defer detail to 11.03 if time is short). Interviewers are listening for the cost model, not for "WebSockets are realtime."
