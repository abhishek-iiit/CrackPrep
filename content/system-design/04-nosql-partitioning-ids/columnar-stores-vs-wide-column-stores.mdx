## Two systems share a name and disagree about everything else

"Columnar" and "wide-column" sound like variations on one idea, and the confusion is common enough to name directly before going further. A columnar store — Redshift, ClickHouse, a Parquet file — is defined by its physical layout: every column's values are stored contiguously, so a query touching three columns out of two hundred reads only those three. A wide-column store — Bigtable, Cassandra, HBase — is a data model, not a layout: rows keyed by a row key, values grouped into named column families, and any row allowed a different set of columns from any other. Underneath, a wide-column store is usually built on the same kind of engine as anything else with a write-heavy path — an LSM tree (07.09 LSM Tree Storage Engine) — which is closer in spirit to a row store than to a columnar file format.

The practical cost of confusing them runs both ways. Reach for Cassandra expecting Redshift's "scan two columns across a billion rows in a second" and you'll be disappointed, because Cassandra's storage is organized for lookup and range scan by row key, not for cheap column-only scans across the whole dataset. Reach for Redshift expecting Cassandra's "accept fifty thousand writes a second from a fleet of devices, each with its own sparse set of columns" and you'll be disappointed the other way — columnar formats are typically built and compressed in batches, and random single-row inserts are exactly what they're worst at.

### Columnar: contiguous by column

For N rows and M columns, a row store puts row 1's M values together, then row 2's, and so on. A columnar store puts all N values of column 1 together, then all N values of column 2. Values in one column share a type and often a narrow range, so they compress far better together than mixed with unrelated types in a row — run-length encoding, dictionary encoding, and delta encoding all get more effective. A scan that needs only `amount` and `region` out of a 200-column events table reads only those two column files, skipping the other 198 entirely: I/O scales with columns touched, not columns that exist. The cost lands on writes — inserting one row means touching all M column files — so columnar engines usually queue writes and flush them as large batches rather than committing rows one at a time.

### Wide-column: sparse, sorted by row key

Think of a wide-column store as a distributed, sorted, multi-dimensional map: row key to column family to column qualifier to a timestamped value. Rows are stored sorted by row key, so a range scan by key — all sensor readings for one device between two times, if the row key is prefixed by device id — is efficient. Columns are sparse and dynamic: one row might have twenty columns in a family, another row three, with no wasted space for the columns a row doesn't have, unlike a fixed-schema table with nullable columns. Physically it's usually an LSM tree per column family: writes append to a memtable and a write-ahead log, flush to immutable sorted files, and compact in the background — 07.09 LSM Tree Storage Engine covers the mechanics directly. That's where a wide-column store's real strength comes from: absorbing very high, continuous write volume, because the foreground write path is the same cheap append that makes any LSM engine fast.

| | Columnar (analytical) | Wide-column (Bigtable/Cassandra) |
| --- | --- | --- |
| What's contiguous on disk | One column's values, across all rows | One row key's columns, within a column family |
| Optimized for | Aggregating a few columns across huge row counts | High-throughput writes and range scans by row key |
| Update pattern | Large batch loads; a single-row update is expensive | Continuous per-row writes, including sparse, partial rows |
| Compression | Very high — same-typed values, run-length and dictionary encoding | Moderate — compresses within a column family, not across the dataset |
| Underlying engine | Columnar file format (Parquet, ORC) plus a query executor | LSM tree, the same family as 07.09 LSM Tree Storage Engine |
| Example systems | Redshift, ClickHouse, BigQuery, Snowflake | Bigtable, Cassandra, HBase |

<Callout type="note">
Some systems blur the boundary on purpose — certain wide-column engines add columnar-like compression within a column family, and some analytical warehouses bolt on fast point-lookup paths beside their columnar storage. Treat a vendor's claim to be "both" as a detail to verify against your actual query pattern, not a reason to skip the distinction above.
</Callout>

Columnar analytical stores earn their place wherever the query is "aggregate over a lot of history, touching few columns" — dashboards, BI, time-window rollups at a scale beyond what a single service's own aggregation, like 10.06 Bucketed Time Window Aggregation, is built to hold. Wide-column stores earn their place wherever the write volume is the constraint and the read pattern is a lookup or range scan by a known row key — time series per device, per-user event history, anything sharded by a natural key with unbounded growth; 04.05 Sharding And Partitioning covers how that row key becomes the partition key in most deployments.

## In an interview

Name the layout, not the label. Saying "wide-column" or "columnar" without describing the physical property you actually need doesn't show reasoning — say "I need to scan two columns across the whole table for a rollup, so I want data stored contiguously by column" or "I need continuous high-volume writes keyed by device id with a range scan by time, so I want an LSM-backed wide-column store." If asked to justify Cassandra over Redshift for a given workload, the deciding fact is almost always the read pattern: a known key versus an unknown aggregate.
