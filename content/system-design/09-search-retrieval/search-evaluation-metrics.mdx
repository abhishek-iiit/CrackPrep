## Feeling that results got better is not a release criterion

Search quality is easy to argue about and hard to measure. One impressive query in a demo does not mean the new BM25 boosts, champion cutoff, or learning-to-rank model (09.05, 09.06, 09.08) improved the system. Another team's favorite query may have gotten worse. **Evaluation metrics** turn ranking into something you can compare across versions: offline against labeled judgments, and online against live user outcomes.

09.01 Information Retrieval System Design already defined precision and recall for sets. Ranking evaluation extends them to *ordered* lists — because showing the right document at position 10 is worse than showing it at position 1, even if both lists contain it. Without that, two systems with identical recall look identical while users experience them as night and day.

## Offline set metrics (unordered)

Given a query, a set of retrieved documents, and a set of known relevant documents:

- **Precision** = |retrieved ∩ relevant| / |retrieved|
- **Recall** = |retrieved ∩ relevant| / |relevant|
- **F1** = harmonic mean of precision and recall

Useful for the retrieval stage (09.03): did boolean + champions still recover the judged relevant docs? Less useful alone for ranking, because they ignore order. A system that puts all relevant docs at ranks 90–100 can score perfect recall@100 and still be unusable.

## Offline ranked metrics

Judgments are usually graded (0 irrelevant … 3 perfect) or binary. Metrics differ in how they reward putting good documents high.

| Metric | What it asks | Notes |
| --- | --- | --- |
| Precision@k | Of the top k, what fraction are relevant? | Simple; ignores order inside k and anything below k |
| Recall@k | Of all known relevant, what fraction appear in top k? | Critical for retrieval-tier changes |
| MRR (Mean Reciprocal Rank) | Averaged 1/rank of first relevant hit | Good when one right answer matters (navigational) |
| MAP (Mean Average Precision) | Mean of per-query average precision over ranks | Classic binary-relevance ranking metric |
| nDCG@k | Normalized discounted cumulative gain | Handles graded relevance; discounts lower ranks |

**DCG** sums `gain(rel_i) / log2(i+1)` over positions `i` in the result list — lower ranks contribute less. **nDCG** divides by the DCG of the ideal ordering of the same judgments, so scores sit in [0, 1] and can be compared across queries with different amounts of relevant material.

<Formula label="Discounted cumulative gain">DCG@k = Σ_&#123;i=1..k&#125; (2^&#123;rel_i&#125; − 1) / log2(i + 1)</Formula>

(The `2^\{rel\} − 1` gain is a common graded formulation; some setups use `rel_i` directly. State which you use.)

**nDCG@k** = DCG@k / IDCG@k. Report at the depth users actually see — nDCG@10 for a ten-blue-link page, nDCG@3 for a mobile product grid. Quoting nDCG@1000 when the UI shows three cards optimizes a fantasy product.

### Worked fragment

Judged relevance for a query's top-4: `[3, 0, 2, 1]` with gains `2^rel − 1` → `[7, 0, 3, 1]`.

DCG ≈ 7/log2(2) + 0/log2(3) + 3/log2(4) + 1/log2(5) = 7/1 + 0 + 3/2 + 1/2.322 ≈ 7 + 1.5 + 0.43 ≈ **8.93**.

Ideal order `[3, 2, 1, 0]` → gains `[7, 3, 1, 0]`; IDCG ≈ 7 + 3/1.585 + 1/2 + 0 ≈ 7 + 1.89 + 0.5 ≈ **9.39**.

nDCG@4 ≈ 8.93/9.39 ≈ **0.95**. Swapping the 0 and the 2 would move DCG materially — that is the metric doing its job.

## Building a judgment set

Metrics are only as honest as the labels:

- **Pooling.** Take top-k from several systems, union, judge the pool — otherwise documents never retrieved by any system look "irrelevant" forever and metrics punish recall innovations unfairly.
- **Query sampling.** Mix head and tail queries from logs; optimizing only head queries abandons the long tail.
- **Inter-judge agreement.** Relevance is subjective; measure agreement and use multiple judges on hard queries.
- **Freshness.** Stale judgments drift from the live corpus (09.10 Search Index Synchronization) — retire or refresh sets on a cadence.

Offline metrics catch regressions before users do. They miss presentation effects, latency, and personalization that only appear in production.

## Online evaluation

| Method | Measures | Risk |
| --- | --- | --- |
| A/B test | CTR, reformulation rate, dwell, conversion | CTR theater without success metrics (09.08) |
| Interleaving | Which system wins pairwise clicks | Sensitive setup; still click-biased |
| Guardrail metrics | p99 latency, empty-result rate, error rate | A "better" ranker that times out is not better |

Run online tests with a primary success metric aligned to the product (purchase, session success) plus guardrails (latency, revenue, complaint rate). Offline nDCG lifts that fail online often mean labels disagree with users — or position bias / caption changes dominated.

<Callout type="tip">
When proposing a ranking change in an interview or a design review, name the metric and the depth up front: "I would gate this on nDCG@10 on a pooled judgment set plus an A/B on purchase rate with latency guardrails." That one sentence signals you know search quality is measured, not asserted.
</Callout>

## In an interview

Define success in one breath: "Offline I care about nDCG@k on graded judgments for ranking and recall@k for retrieval changes; online I A/B a success metric with latency guardrails — not CTR alone." If they ask how you get labels, say pooling from multiple rankers and sampling head+tail queries.

Name a failure mode unprompted: optimizing precision@3 can hide a recall collapse from an aggressive champion list — always watch a recall-oriented metric when touching 09.03/09.06. That diagnostic split mirrors "missing doc vs wrong order" from 09.01.
