## Finding the node that owns the key

Before a client can read `user:42`, something has to answer "which machine, which port, which epoch." That answer is **discovery**. When the answer is not just addresses but the authoritative map of shards, replicas, schema versions, and leaders, the component holding it is a **metadata service** — HDFS NameNode, Kafka's controller-managed metadata, Chubby/etcd-backed assignment maps, the DynamoDB partition metadata path, object-store namespace services (07.17 Metadata DB For Object Storage).

Get the data path wrong and one request fails. Get metadata wrong and a whole region double-writes, or every client pounds a dead primary, or a rebalance deletes the wrong replica. Metadata volume is tiny compared to user data; its correctness requirement is not. That asymmetry — small, hot, must be right — is why metadata so often sits on consensus (06.06 Consensus) while the bytes live on cheaper replication (06.03 Replication).

## Discovery mechanisms, from soft to hard

**DNS and load balancers.** Clients resolve a name; the LB fans out to healthy backends. Fine for stateless services where any instance will do. Terrible as the only story for "who owns shard 17," because DNS TTLs and LB health checks lag leadership changes and cannot fence stale writers.

**Client-side service discovery.** A library watches a registry (Consul, etcd, Eureka-style) and picks an instance locally. Faster failovers than DNS TTL when watches are prompt; still only as correct as the registry's guarantees.

**Gossip membership (06.11 Gossip Protocol).** Decentralized view of who is alive and which tokens they advertise. Excellent hinting layer for large clusters; not the system of record for assignments that must not fork.

**Strongly consistent metadata service.** Membership, leader, and partition map are stored in a Raft/Zab/Paxos group (or a single Active NameNode with a journal). Clients read the map (often cached with a version), and writes that change topology go through the metadata leaders. This is the pattern when misrouting corrupts data.

| Layer | Typical guarantee | Stale answer cost | Role |
| --- | --- | --- | --- |
| DNS / LB | Best-effort health | Retry another instance | Stateless service entry |
| Registry watch | Depends on store | Brief misroute | Service discovery |
| Gossip view | Eventual | Dual views under partition | Large-cluster hints |
| Consensus metadata | Linearizable updates | High if clients skip versioning | Shard map, leaders, ACLs |

## What the metadata plane must provide

A useful metadata service is more than a phone book:

- **Assignments** — which nodes replicate which partitions, and who is primary (06.07 Leader Election).
- **Versions / generations** — so clients and data nodes can reject stale maps; fencing tokens belong here or in the same epoch space.
- **Leases and sessions** — so a dead node's assignments can be revoked without waiting for an operator.
- **Change notification** — watches or push so caches invalidate in seconds, not after a 60s TTL.
- **Bootstrap** — seeds for new nodes (often a static list pointing at the metadata quorum itself).

Caching is mandatory for performance — every data request should not round-trip etcd — and dangerous without versions. The safe pattern: cache the map with a metadata epoch; on redirect or fencing rejection, invalidate and refetch. Treating a cached primary address as eternal is how split brains get traffic after failover.

<Callout type="warn">
Putting the metadata service in the same failure domain as a single data node — one disk, one rack, one AZ — means a routine hardware failure takes down addressing for the whole cluster. Metadata quorums are small; place them for independence, and practice minority loss (what happens when two of five etcd members die).
</Callout>

## Control plane versus data plane

Keep the paths separate in the design conversation. Clients discover via metadata, then speak to data nodes on a different path. Bulk data does not flow through etcd. Rebalances update metadata first (or in a coordinated dance with data copy), then clients learn the new owner. When people say "the NameNode is the bottleneck," they usually mean either CPU on the metadata leader under too many tiny ops, or an architecture that required metadata on every read — both are design smells, not reasons to make metadata eventually consistent without a plan for conflict.

Stateless microservices can often stop at DNS + registry. Stateful systems almost always grow a real metadata plane the moment they shard.

## In an interview

Split the board: "control plane metadata versus data plane." Say the shard map lives in etcd/Raft (or equivalent), clients cache it by version, and data RPCs carry an epoch so stale owners get rejected. Discovery for stateless frontends can stay DNS. Expect "what if metadata is down?": the honest answer is that many stateful clusters degrade or freeze topology changes — which is why the metadata quorum is sized and placed like a critical dependency, not like a best-effort cache. Cross-link gossip as the hint layer and consensus as the authority when both appear in the design.
