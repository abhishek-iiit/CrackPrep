## Callers that know too much about your data structure

A dashboard lists products from an in-memory array today. Next quarter the catalog moves to a paginated API, then a lazy database cursor, then a composite tree of categories and SKUs. Every screen that wrote `for (let i = 0; i < products.length; i++)` breaks — not because the data changed, but because the **traversal contract** was never separated from the **storage shape**.

Iterator fixes that by giving clients a narrow interface: start, next, done, current item. The collection hides whether it is a linked list, a B-tree, or a remote page fetcher. The loop code stays the same; only the factory that hands out iterators changes.

## Iterator, iterable, and the traversal protocol

Two sides of the same idea:

- **Iterator** — object with `next()` returning `{ value, done }` (ECMAScript) or equivalent (`hasNext`/`next` in Java).
- **Iterable** — collection that can produce a fresh iterator via `Symbol.iterator` or `iterator()`.
- **Client** — consumes via `for...of`, `foreach`, or manual `while (!done)`.

<Steps>
<Step title="Collection implements iterable">
`[Symbol.iterator]()` returns a new iterator instance. Each traversal gets its own cursor — two simultaneous loops do not share state.
</Step>
<Step title="Iterator holds traversal state">
Index, stack of tree nodes, or HTTP page token — whatever the structure needs. The client never sees it.
</Step>
<Step title="Client walks until done">
Standard loop constructs compile down to iterator calls. Filter and map become iterator adapters wrapping the source.
</Step>
</Steps>

```typescript
class PageCursor<T> implements Iterable<T> {
  constructor(private fetchPage: (token?: string) => Promise<{ items: T[]; next?: string }>) {}
  async *[Symbol.asyncIterator]() {
    let token: string | undefined;
    do {
      const page = await this.fetchPage(token);
      for (const item of page.items) yield item;
      token = page.next;
    } while (token);
  }
}
```

Language runtimes ship this pattern built in — Java `Iterable`, C# `IEnumerable`, Rust `IntoIterator`. Custom iterators matter when you wrap legacy structures, lazy streams, or graph walks that do not fit a bare array.

<Callout type="note">
Removing an element through an iterator while traversing invalidates the cursor in most implementations — ConcurrentModificationException in Java, undefined behaviour in hand-rolled lists. Fail fast or document copy-on-iterate semantics explicitly.
</Callout>

## External vs internal iteration

**External** — the client drives the loop (`for (const x of coll)`). **Internal** — the collection drives it (`coll.forEach(fn)`). Internal iteration is simpler but cannot easily `break` mid-stream or compose lazy pipelines without language support. Generators in modern JavaScript and Python blur the line — lazy `map` over an iterator is external iteration with sugar.

When traversal order matters (sorted, depth-first, breadth-first), encode it in the iterator implementation, not in every caller.

<Tradeoff
  forTitle="Reach for a custom iterator when"
  againstTitle="Skip custom iterators when"
  forItems={[

    "You must hide a legacy internal representation from new modules during a migration",
    "Several algorithms share the same walk and centralising cursor logic prevents drift",

## In an interview

This pattern rarely needs the GoF name — say "I would expose an iterator so UI code does not depend on whether products live in an array or a paginated API." Expect "Iterator vs Visitor" (03.10 Visitor operates on typed nodes with double dispatch; Iterator simply yields elements). Mention fail-fast on concurrent modification if the structure is mutable. The misuse is wrapping an array in six classes when `for...of` already works.
